# Eyeriss：面向深度卷积神经网络的高能效可重构加速器

**原文题名**：Eyeriss: An Energy-Efficient Reconfigurable Accelerator for Deep Convolutional Neural Networks（2016，DOI: 10.1109/jssc.2016.2616357）

## 一、作者要证明什么

这篇论文的核心主张可以概括为一句话：**对于 CNN 推理加速器，决定能效的关键不是计算本身，而是数据搬运；通过一种可重构的数据流（dataflow）把数据尽量留在低能耗的存储层级里复用，就能在支持多种 CNN 形状的同时显著降低系统能耗。** 作者用一颗 65-nm 流片芯片 Eyeriss 来支撑这一主张，并用 AlexNet 与 VGG-16 两个公开 CNN 的实测数据作为证据 [page 1][page 9]。

这个主张包含几个必须分别成立的支撑结论：

1. **数据搬运比计算更耗能**，因此优化目标应是整个系统（芯片 + 片外 DRAM）的能耗，而非仅芯片功耗 [page 1]。
2. **Row Stationary（RS）数据流**能同时最小化 ifmap、filter、psum 三类数据的搬运，并适配不同 CNN 形状 [page 3]。
3. **利用 CNN 数据中的零**（压缩与数据门控）可以进一步省能耗 [page 6][page 9]。
4. 上述机制在真实芯片上确实带来了可测量的能效与 DRAM 访问量改善 [page 9][page 10]。

下面按论证链条展开。

## 二、论证的起点：为什么盯住"数据搬运"

作者在引言中给出的推理是：现代 CNN 单次推理需要数十到数百 MB 的参数和数十亿次运算，这会产生大量片上与片外数据搬运；而数据搬运可能比计算本身更耗能 [page 1]。因此，要同时获得高吞吐和高能效，硬件必须既提供高并行度，又针对整个系统的数据搬运做优化，并且这种优化要能适应 CNN 高维卷积形状的变化 [page 1]。

这里有一个关键的**量级论证**，出现在结果部分而非引言：在实测功耗分解中，ALU 只占总功耗不到 10%，而数据搬运相关部件（spads、GLB、NoC）占到最多 45% [page 10]。作者据此明确写道"这证实了数据搬运比计算更耗能" [page 10–11]。也就是说，引言中的前提在结果部分得到了芯片级证据的回填。这是全文论证的支点：**如果数据搬运不是主要能耗来源，那么 RS 数据流的整套设计就失去了意义。**

## 三、RS 数据流：从"复用"到"少搬"

### 3.1 三类复用与一个内在矛盾

作者先列出 CNN 中三种可被利用的数据复用 [page 3]：

- **卷积复用（convolutional reuse）**：每个 filter 权重在同一 ifmap 平面内被复用 E×F 次；每个 ifmap 像素在同一 filter 平面内通常被复用 R×S 次。
- **filter 复用**：每个 filter 权重跨 batch 的 N 张 ifmap 复用。
- **ifmap 复用**：每个 ifmap 像素跨 M 个 filter 复用（生成 M 个 ofmap 通道）。

同时，为了减少 psum 搬运，理想情况是尽快把 C×R×S 个值累加成一个 ofmap 值。但作者指出一个**内在矛盾**：最大输入复用与立即 psum 归约无法同时实现，因为用同一 filter 或 ifmap 值产生的 psum 之间不可归约 [page 3]。RS 数据流正是为同时优化所有数据类型而提出的系统性方案。

### 3.2 关键推理步骤：把 2-D 卷积拆成 1-D 原语

RS 的核心操作是：把公式 (1) 的计算拆成可并行的 **1-D 卷积原语**，每个原语处理一行 filter 权重和一行 ifmap 值，产生一行 psum；每个原语映射到一个 PE，于是"每一行对"的计算就**驻留（stationary）**在 PE 内 [page 3]。

这一步是全文最关键的设计转折。由于原语采用滑动窗口处理（Fig. 3），PE 只需保留一个滑动窗口的数据，因此所需 spad 容量只取决于 filter 行大小 S，而与 ifmap 行大小 W 无关：filter 需 S、ifmap 滑动窗口需 S、psum 累加需 1 [page 3]。作者随即用 AlexNet 验证：S 的可能取值为 11（CONV1）、5（CONV2）、3（CONV3–CONV5），因此支持所有层所需的最小 spad 容量为 filter 11、ifmap 11、psum 1 [page 3]。

**这里的桥接是**：spad 容量小 → 数据可以留在最便宜的存储层级 → 高成本层级（GLB、DRAM）的访问被削减。作者没有在每一处都重复这条因果链，但它是 RS 省能的机制基础。

### 3.3 从 1-D 到 2-D：PE Set 与三种方向性复用

多个 1-D 原语组成 2-D 卷积时，会共享同一行 filter 或 ifmap，并把多个原语的 psum 累加。作者据此把 PE 分组为 **PE Set**（Fig. 4）：在一个 set 内，filter 行**水平**复用、ifmap 行**对角**复用、psum 行**垂直**累加 [page 4]。PE set 的尺寸由该层的 filter 和 ofmap 尺寸决定：高 = filter 行数 R，宽 = ofmap 行数 E。AlexNet 中 PE set 尺寸为 11×55（CONV1）、45×27（CONV2）、3×13（CONV3–CONV5）[page 4]。

### 3.4 映射到物理阵列：两个例外与 strip mining

PE set 尺寸是层形状的函数，与物理阵列尺寸无关，因此需要映射策略。作者给出两个例外 [page 4]：

1. **PE set 超过 168 个 PE**：用 strip mining，一次只处理 e 行 ofmap（e ≤ E），尺寸变为 R×e。
2. **PE set 小于 168 但宽 > 14 或高 > 12**：过宽的 set 被切成独立段分别映射；Eyeriss 不支持高于阵列的 set，因此**原生支持的最大 filter 高度为 12** [page 4]。

Fig. 5 展示了 AlexNet 五层的映射：CONV1 的 11×55 被 strip-mine 成 11×7；CONV2 的 5×27 被切成 5×14 和 5×13 两段；CONV3–CONV5 的 3×13 直接放入 [page 4]。这里 strip-mined set 的宽度由一个"优化整体能效"的过程决定，作者引用 [32] 而未在本文展开 [page 4]。

### 3.5 处理 2-D 之外的三个维度

公式 (1) 还有 batch（N）、通道（C）、filter 数（M）三个维度。作者的处理方式是：每次只变化一个维度、固定其余两个，于是两个 2-D 卷积之间要么复用同一 filter、要么复用同一 ifmap、要么可累加 psum [page 4]。具体实现为 [page 5]：

- **filter 复用**：把不同 ifmap 顺序流过同一 PE set（Fig. 6(a)）。
- **ifmap 复用与 psum 累加**：用 spad 或 PE 阵列的空间并行性实现（Fig. 6(b)(c)）。

作者用参数 **p、q** 描述单个 PE 内同时运行的多个原语：每个 PE 同时跑来自 p 个不同 filter、q 个不同通道的 p×q 个原语。所需 spad 容量为：filter 为 p×q×S，ifmap 为 q×S，psum 为 p [page 5]。在 Eyeriss 的 spad 配置下（ifmap spad 12 b×16 b、filter spad 224 b×16 b、psum spad 24 b×16 b），AlexNet 中 p 最大 24、q 最大 4（因最小 S 为 3）[page 5]。

用参数 **r、t** 描述阵列中并行的多个 PE set：阵列可容纳 r×t 个 set，运行 r 个通道、t 个 filter；每 t 个 set 共享同一 ifmap，每 r 个 set 在阵列内累加 psum [page 5]。Fig. 5 中 CONV1 和 CONV3 的 t 分别为 2 和 4，CONV4、CONV5 的 r = t = 2 [page 5]。未被任何 set 覆盖的 PE 被时钟门控以省能 [page 5]。

### 3.6 Processing Pass 与 GLB 的可重构分配

一次"处理遍（processing pass）"中，每个输入数据只从 GLB 读一次，psum 只在处理结束时写回 GLB 一次 [page 5]。一个 CNN 层通常需要数百到数千个 pass，跨 pass 的 ifmap 复用和 psum 累加由 GLB 缓冲实现：ifmap 可跨多个 pass 复用，psum 用 GLB 作中间存储，直到得到最终 ofmap 才离开芯片 [page 6]。

Fig. 7 用一个示例层（C=6、M=8、N=4，每 pass 处理 3 通道、4 filter、n=2）说明调度：共 8 个 pass，每组 ifmap 从 DRAM 读一次、在 GLB 中复用两次，GLB 需存 m=8 个 ofmap 通道的 psum [page 6]。由此得出 GLB 必须存储 n×q×r 个 2-D ifmap 和 n×m 个 2-D psum，且分配比例需可重构 [page 6]。Table II 汇总了 RS 数据流的映射参数，Table III 给出 AlexNet 在 Eyeriss 上的具体参数（假设 batch N=4）[page 6][page 7]。

## 四、利用数据统计：压缩与门控

RS 数据流优化的是"搬运多少"，而数据统计优化的是"能不能少搬、少算"。

作者给出零值统计：ReLU 把负值整流为零，零值比例随层加深而增加；AlexNet 中 CONV2 的 ifmap 平均约 40% 为零，到 CONV5 升至约 75% [page 6]。此外引用 [33] 指出 CNN 中 16%–78% 的 filter 权重可被剪枝为零 [page 6]。

**RLC（run-length compression）**：连续零（最大游程 31）用 5-b Run 表示，下一个值直接作为 16-b Level 插入，每三对 run/level 打包进一个 64-b 字，最后一位标记是否为末字（Fig. 8）[page 6]。作者报告，基于 AlexNet + ImageNet 的实验，RLC 的压缩率仅比理论熵极限多 5%–10% 开销 [page 6]。除第一层输入外，所有 fmap 都以 RLC 压缩形式存于 DRAM [page 6]。实验显示 fmap 的 DRAM 访问在 CONV1 可省近 30%、在 CONV5 可省近 75%；Fig. 9 给出 RLC 前后 AlexNet 总 DRAM 访问对比（含 filter、ifmap、ofmap）[page 6]。作者也指出，若对 filter 权重也应用 RLC，DRAM 访问可进一步降低 [page 6]——这是一个**未实现的潜在改进**，而非已测结果。

**数据门控（data gating）**：PE 内用额外 12-b Zero Buffer 记录 ifmap spad 中零的位置；检测到零时，门控逻辑禁止读 filter spad 并阻止 MAC 数据通路翻转（Fig. 12 红色路径）[page 9]。相比无门控的 PE 设计，可省 45% 的 PE 功耗 [page 9]。

## 五、证据如何支撑结论：实测结果

### 5.1 芯片与配置

Eyeriss 在 65-nm CMOS 实现（Fig. 13），已集成进 Caffe 框架（Fig. 14）[page 9]。1 V 下峰值吞吐 33.6 GMAC/s，核心时钟 200 MHz [page 9]。作者称多数先进 CNN 的形状落在 Eyeriss 原生支持范围内，无需修改即可加速 [page 9]。

面积分解（Fig. 15）：所有 PE 的 spad 占近一半总面积，是 GLB 的 2.5 倍，但 spad 总容量比 GLB 小 1.5 倍；片上存储（GLB + 所有 spad）占总面积三分之二，而 168 个 PE 的乘法器和加法器仅占 7.4% [page 9]。这组数据本身就在强化"存储/搬运主导"的叙事。

### 5.2 AlexNet

Table V 给出五层 CONV 的实测分解（1 V，N=4，核心/链路时钟 200/60 MHz）[page 9][page 10]。平均帧率 34.7 frames/s，等效吞吐 23.1 GMACS，实测芯片功耗 278 mW，能效 83.1 GMACS/W [page 9]。实际吞吐低于峰值有三个原因：仅 88% 的 PE 活跃；每个 pass 从 GLB 加载数据到 PE 阵列有 ramp-up 时间；加载 ifmap 或写回 ofmap 时芯片不处理 [page 9–10]。作者指出最后一点可通过更精细的 DRAM 流量控制以极小代价优化，因此额外给出"Processing Latency"列，表示 DRAM 流量与处理完全重叠时的性能 [page 10]。对一批四帧，所需 DRAM 访问为 15.4 MB，即 0.0029 access/MAC（37.4 access/input pixel）[page 10]。

功耗分解（Fig. 16）：CONV5 中 spad、乘法器加法器功耗远低于 CONV1，因 ifmap 中的零更多；总体上 ALU 占总功耗不到 10%，数据搬运相关部件占最多 45% [page 10]。电压缩放（Fig. 17）：1.17 V 时最大吞吐 45 frames/s，0.82 V 时最大能效 122.8 GMACS/W [page 11]。

### 5.3 VGG-16

Table VI 给出 13 层 CONV 的实测分解（1 V，N=3）[page 11]。平均 0.7 frames/s，实测功耗 236 mW [page 11]。帧率低于 AlexNet 主要因 VGG-16 每帧计算量是 AlexNet 的 23 倍 [page 11]。作者给出一个有意思的对照：CONV1-2 与 CONV4-2 的 MAC 运算量相同，但前者耗时约为后者的四倍，原因是早期层需要更多 processing pass，因而在 PE 阵列 ramp-up 上花更多时间；pass 数多由大 fmap 尺寸决定 [page 11]。一批三帧所需 DRAM 访问为 321.1 MB，即 0.0035 access/MAC（1066.6 access/input pixel）[page 11]。

## 六、结论成立的条件、边界与局限

**成立条件（作者明说或可从文本直接读出）**：

- 结论依赖"数据搬运比计算更耗能"这一前提，而该前提在本文中由 Fig. 16 的功耗分解在 AlexNet 上得到支持 [page 10]。若换到数据搬运占比不高的负载，RS 的收益逻辑会减弱——这是分析推断，非作者原话。
- 能效数字绑定具体配置：AlexNet 的 278 mW、83.1 GMACS/W 对应 N=4、1 V、200/60 MHz [page 9]；VGG-16 的 236 mW 对应 N=3 [page 11]。作者说明这两个 batch size 是依据 [32] 的优化在 Eyeriss 上能效最高的选择 [page 9]。
- 帧率与 DRAM 访问量是"实测"与"重叠假设"两种口径并存：Table V 同时给出实测帧率和 Processing Latency，后者假设 DRAM 流量与处理完全重叠 [page 10]。引用数字时需区分。

**作者承认的局限**：

- Eyeriss 不支持高于 PE 阵列的 PE set，原生最大 filter 高度为 12 [page 4]。
- 实际吞吐低于峰值，部分因 DRAM 加载/写回期间不处理；作者称可通过精细控制优化，但本文未实现 [page 9–10]。
- RLC 未应用于 filter 权重，作者明说"若应用可进一步降低 DRAM 访问" [page 6]——即当前结果未包含这部分潜在收益。

**需要谨慎对待之处**：

- 摘要中给出的 AlexNet 数字为 35 frames/s、0.0029 DRAM access/MAC、278 mW（N=4），VGG-16 为 0.7 frames/s、0.0035 DRAM access/MAC、236 mW（N=3）[page 1]；正文 Table V 的平均帧率为 34.7 frames/s [page 9]。两者一致（四舍五入），无矛盾。
- 文中"1.4–2.5 倍更省能"（相对已有数据流，AlexNet）[page 3] 依赖引用 [32] 的优化与对比方法，本文未展开该对比的细节，因此这一倍数应视为作者转述其优化框架的结论，而非本文独立复现的对照实验。
- 数据门控"省 45% PE 功耗"[page 9] 是与"无门控 PE 设计"的对比，属 PE 级而非系统级，不能直接等同于整芯片省 45%。

## 七、一句话总结论证结构

作者先立起"数据搬运主导能耗"的前提，再用 RS 数据流把 2-D 卷积拆成驻留 PE 的 1-D 原语、以 PE set 和 p/q/r/t 参数在四个存储层级间最大化复用，从而把高成本层级（GLB、DRAM）的访问压到最低；RLC 与数据门控进一步利用 CNN 的零值统计；最后用 AlexNet 与 VGG-16 的流片实测功耗、帧率和 DRAM access/MAC 证明这套机制在真实芯片上成立。结论的强度受限于：它绑定于"搬运主导"的负载特征、特定的 batch/电压/时钟配置，以及若干作者明说未实现或未展开的优化与对比。
