# StarPU：面向异构多核架构的统一任务调度平台

**原文题名**：StarPU: a unified platform for task scheduling on heterogeneous multicore architectures
**年份**：2010（在线发表），2011 年正式刊于 *Concurrency Computat.: Pract. Exper.* 23:187–198
**DOI**：https://doi.org/10.1002/cpe.1631

## 论文要解决的问题与核心主张

这篇论文的出发点是一个硬件趋势判断：HPC 架构正在从同构多核走向"多核 + 专用协处理器（如 Cell/BE 的 SPU）+ 数据并行加速器（如 GPU）"的异构组合，而现有的主流编程标准（MPI、OpenMP）无法覆盖这类机器的全部需求，OpenCL 虽然提供了统一接口，但层次太低——它只提供显式卸载任务和搬运数据的原语，不提供任务调度，也不维护全局数据一致性，因此作者认为它更像"虚拟设备驱动"而非真正的运行时系统 [page 2]。

作者的核心主张是：可以设计一个运行时系统 StarPU，用**统一的执行模型**同时抽象多核 CPU 与各类加速器上的任务执行，用**统一的数据管理库**自动处理跨设备的数据移动与一致性，并在此之上提供一个**可插拔的调度框架**，让调度策略独立于应用、可在运行时选择。作者进一步主张，借助性能模型驱动的动态调度，StarPU 不仅能显著改善执行时间，还能在异构平台上获得"超线性"的并行效率，并在可移植性上胜过高度手工优化的静态方案（MAGMA）[page 1]。

## 统一执行模型与数据管理：论证的地基

论文的论证链条从抽象层开始。StarPU 把"任务"定义为可在 CPU 核上执行、也可异步卸载到加速器上的计算单元；程序员可以为同一任务提供多个目标平台的实现（用 CUDA、BLAS 等），这些实现的集合就构成该任务的抽象 [page 3]。任务结构里包含对每块被操作数据的高层描述及其访问方式（R、W、R/W），因此 StarPU 既能借助数据管理库强制数据一致性，又能让程序员用很少的代价表达复杂的任务依赖图；由于任务是异步启动的，StarPU 还能在有利于性能时对任务重排序 [page 3]。

数据管理部分承接作者此前的工作 [1]：用软件 MSI 缓存协议最小化传输次数，用分区函数和驱逐启发式应对加速器内存有限的问题 [page 3]。这一层是后面所有调度论证的前提——正因为数据移动被自动且一致地管理，调度器才可能把"数据局部性"和"传输开销"纳入决策，而不必让应用自己操心。

移植性方面，作者声称支持一个新架构只需实现两件事：主机与加速器之间的内存传输函数，以及真正执行/卸载任务的方法。该模型已在多核处理器、CUDA GPU 和 Cell 处理器上实现 [page 3]。这是"统一"主张的直接证据，但注意这里给出的是实现范围的陈述，而非跨平台的定量对比。

## 调度框架：把调度理论接到真实机器上

论文把调度设计成一个队列抽象：每个 worker（计算资源）对应一个抽象任务队列，队列上只有两个操作——提交（push）和取任务执行（pop）；队列可以是共享的、每 worker 独立的，拓扑可以是中心队列或分布式队列，具体实现（FIFO、栈、优先队列、deque）由策略决定 [page 4]。作者明确把已实现的策略限定在**贪婪列表调度**范式内：当一个就绪任务（依赖全部满足）被提交时，直接插入某个队列，且不重新考虑既有决策；未就绪的任务不参与调度，而是在其最后一个依赖完成时由 StarPU 调用 push 触发调度 [page 4]。作者承认这一限制可能降低调度引擎的通用性，但认为它足够简单，从而能实现可移植的策略，并让调度理论研究者把 StarPU 当作实验平台 [page 4]。

Table I 列出了用该接口实现的策略：greedy（支持优先级）、no-prio、ws（基于工作窃取）、w-rand（按处理器速度加权随机）、heft-tm（异构最早完成时间，HEFT [3]）[page 4]。作者强调这些策略通常用不到 100 行 C 代码写成，以此佐证接口的简洁性 [page 5]。

调度提示（hints）是连接理论与机器的关键设计。作者允许程序员在任务结构里加入两类可选信息：任务优先级，以及性能模型（为依赖图加上权重）[page 4–5]。性能模型可以来自预校准、历史执行结果，或运行时动态调整；作者特别指出，异构性使性能预测更复杂，因为同一任务在不同架构上可能用不同算法实现、复杂度不同，因此可以为每个架构分别建立性能模型 [page 5]。这一节为第 4 节的实验埋下伏笔：论文要比较"平均加速比模型"和"逐任务精确模型"两种做法的效果。

## 实验如何支撑结论

实验平台是两台各含 E5410 Xeon 四核（2.33 GHz，4 GB 内存）的机器，分别配 NVIDIA Quadro FX4600（768 MB）和 FX5800（4 GB），运行 Linux 2.6 与 CUDA 2.3，使用 ATLAS 3.8 与 CUBLAS 2.3；由于 CUDA 的限制，一个核被专门用于控制 GPU，因此在第一台机器上实际是"三核 + 一个 GPU"同时计算 [page 5]。测试程序是分块矩阵乘法、分块 Cholesky（无主元）和分块 LU（有/无主元），都是计算密集型（BLAS3 内核，O(n³) 运算对 O(n²) 访存），性能以 GFLOP/s 表示，作者明确说明在异构平台上加速比不适用 [page 5–6]。

**贪婪策略的失败与性能模型的必要性。** 图 1 显示，简单贪婪策略在小矩阵乘法上只有约 50 GFLOPS，中等规模约 225 GFLOPS；作者把低效归因于严重的负载不均衡——CPU 会在 GPU 即将空闲时抢先抓取任务，而 GPU 执行该任务快得多，结果 GPU 完成后 CPU 还要花很久收尾 [page 6]。这里的关键推理是：如果 GPU 比 CPU 快 n 倍，就应给 GPU 分配约 n 倍的任务量。w-rand 策略正是按与 worker 速度成比例的概率随机分配任务，适合等大小的独立任务；但图 1 的阴影区显示其性能波动极大（去掉首尾十分位后仍如此），且由于缺乏负载均衡机制，大规模问题上的平均值反而比贪婪策略更差 [page 6]。作者由此得出一个重要的中间结论：既需要能考虑异构性的策略（如 w-rand），也需要负载均衡机制——这正是 heft-tm 要提供的 [page 6]。

**逐任务精确模型的效果。** heft-tm 用 HEFT 算法 [3]，根据任务在各架构上的预期时长，把它分配给能使完成时间最小的处理单元，同时考虑该 worker 已承担的工作量 [page 7]。图 1 显示，即便独立任务数量有限，矩阵乘法也几乎总能达到接近最优的执行；该策略把中小规模问题的性能提升最多两倍，大规模问题上与贪婪策略相近（因为大输入下贪婪策略的负载不均衡不严重）[page 7]。图 2(a) 显示 LU 分解在"3 CPU + FX5800"上性能显著提升，小规模问题执行时间减半、渐近速度提高；图 2(b) 用较慢的 GPU（FX4600）时 heft-tm 仍最好，而贪婪策略因该 GPU 相对加速比有限、负载不均衡风险降低而几乎一样快，但性能不稳定 [page 7]。作者还指出 heft-tm 对优先级任务支持有限，这在 Cholesky 上是个短板 [page 7]。

**对模型误差的鲁棒性。** 图 3 对性能预测施加随机扰动：调度时不使用真实预测长度 P，而用 P·ln(P)（其中乘一个在 [1−ε, 1+ε] 上均匀选取的随机变量，ε 为扰动幅度）[page 7–8]。结果显示 5% 的扰动只带来很小的性能退化，需要相当严重的误预测才能让 heft-tm 被不用性能模型的策略超过 [page 8]。作者还引用此前工作 [6] 称，自动构建的性能模型对规则内核（如 BLAS3）的预测通常在真实执行时间的 1% 以内，因此程序员无需额外努力即可获得 heft-tm 的收益 [page 8]。这里需要注意：1% 的精度是引用文献 [6] 的结果，不是本文新测的数据。

**优先级提示的作用有限但可移植。** Table II 给出 2.3 GB 单精度矩阵分解的结果：Cholesky 在"3 CPU + FX5800"上从 230.55±0.69 提升到 238.16±1.38 GFlop/s（增益 3.3%），在 FX4600 上从 101.13±0.44 到 104.77±0.47（3.6%）；LU 的增益只有 0.5% 和 1.8% [page 8]。作者解释 LU 计算量是 Cholesky 的两倍，且所用 heft-tm 本身已在减少负载不均衡，因此优先级带来的额外改善有限；但两个平台上行为相似，说明 StarPU 能以可移植方式利用这类提示 [page 8]。

**超线性效率的机制。** 作者把效率定义为"各架构单独获得的算力之和"与"同时使用所有架构获得的算力"之比 [page 8]。图 4(b) 显示 LU 分解中不同任务的加速比差异很大：矩阵乘法（DGEMM）特别高效，而主元选取（pivoting）效率很低，加速比仅 1.2；作者指出相对加速比有限是因为 CPU 双精度 BLAS（ATLAS）已接近峰值，而 CUBLAS 与 FX5800 在双精度上尚未充分优化 [page 8]。图 4(a) 显示混合平台的性能在某些情况下超过各部件单独性能之和，即"超线性效率"。作者给出三个解释因素：性能模型带来的良好负载均衡大幅减少了空闲；StarPU 执行任务的额外开销（通常几微秒）相对 CUDA 自身开销（启动内核或发起内存传输通常至少六微秒 [7]）很小；逐任务性能模型让 heft-tm 按任务在各单元上的实际效率分配工作 [page 8]。图 4(c) 显示任务倾向于被分配到最有效的地方——矩阵乘法更可能卸载到 GPU，三角系统求解在 CPU 上相对更高效，而对角块分解因处于并行算法的关键路径上、耗时很长，总是放在 GPU 上执行 [page 9]。作者总结说，StarPU 以有限的并行开销削弱了 Amdahl 定律的影响，逐任务性能模型让调度引擎把任务派往最有效之处同时保持并行性，因此能观察到超线性效率，且无需程序员提供任何支持 [page 9]。

**与 MAGMA 的对比。** 图 5 比较单 Nehalem CPU 加 Quadro FX5800 上带部分主元的 LU 分解（SGETRF），分别用 StarPU 和 MAGMA [8]。两者 GPU 侧都用 CUBLAS 内核、CPU 侧都依赖 GotoBLAS，但作者的实现以直接、未优化的方式调用这些内核；MAGMA 使用静态调度和高度手工调优的实现，且针对小规模问题专门优化 [page 9]。中等规模问题上 MAGMA 通常只比作者这个简单且可移植的实现快约 25%；但 MAGMA 要求整个矩阵能放进 GPU 内存才能高效地静态求解，而 StarPU 凭借动态调度能透明地分解任意大的矩阵 [page 9–10]。作者据此论证：考虑到开发 MAGMA 所需的巨大投入，这说明动态方法在可移植性能与生产力上都有显著优势 [page 10]。

## 相关工作定位

作者把 StarPU 与 Charm++、Harmony、StarSs、Anthill 等系统对比 [page 10]。要点是：Charm++ 支持 GPU 和 Cell，但作者称尚无性能评估；Harmony 考虑带性能模型的任务调度，但不接受用户提供的调度策略，且 StarPU 因数据管理与调度器紧密集成而能支持更简单、更准确的基于历史的性能模型；StarSs 为每个平台用独立运行时（SMPSs、GPUSs、CellSs），任务卸载由程序员决定，而 StarPU 的任务可无差别地在多个目标上执行；Anthill 与 StarPU 最接近，但其调度只考虑相对加速比，而 StarPU 因数据管理与任务调度紧密集成，能把数据移动开销纳入调度决策 [page 10]。作者据此声称"据我们所知，我们的工作是第一个对配备加速器的异构机器上的可移植任务调度进行深入研究的工作" [page 10]。

## 结论成立的条件与边界

论文的结论有明确的适用范围，需要与主张本身区分开。

其一，**实验规模与硬件范围有限**。所有实验都在两台特定配置的机器上完成，GPU 型号为 FX4600 与 FX5800，CPU 为 Xeon E5410，软件栈为 CUDA 2.3、ATLAS 3.8、CUBLAS 2.3 [page 5]。作者没有给出在其他加速器（如 Cell）上的定量调度结果——Cell 只在"模型已成功实现"的意义上被提及 [page 3]。因此"可移植"这一主张在调度性能层面主要有多核 + CUDA GPU 的证据支撑。

其二，**调度范式被限定为贪婪列表调度**。作者明确承认这一限制可能降低通用性，并把它作为换取可移植性和简洁性的代价 [page 4]。这意味着论文的调度结论不适用于需要重新考虑既有决策或调度未就绪任务的 DAG 调度策略。

其三，**性能模型依赖任务的可预测性**。heft-tm 的优势建立在逐任务性能模型之上，而作者引用的 1% 预测精度是针对规则内核（如 BLAS3）的 [page 8]；对不规则访存或算法复杂度随架构变化的任务，模型精度和调度收益都可能下降。图 3 的扰动实验说明调度对中等程度误预测有鲁棒性，但这是对预测误差的敏感性分析，不等于对模型完全缺失的鲁棒性。

其四，**超线性效率的机制解释是作者给出的、基于间接证据的推断**。图 4(a) 显示混合性能超过各部件之和，图 4(b)(c) 显示任务按效率分布，作者据此归因于负载均衡、低开销和逐任务模型 [page 8–9]。这些因素与超线性现象一致，但论文没有做分离各因素的受控实验，因此"超线性"的因果分解应视为作者的解释而非被独立验证的结论。

其五，**与 MAGMA 的对比不是同类比较**。作者自己说明其内核调用方式直接、未优化，而 MAGMA 高度手工调优且针对小问题优化 [page 9]；因此"中等规模仅慢 25%"这一结果说明的是可移植动态方法相对手工静态方法的竞争力，而非两种实现在同等优化程度下的性能差距。MAGMA 要求矩阵装入 GPU 内存这一限制，是作者论证动态调度优势的关键对照点 [page 9–10]。

最后，论文的"统一平台"主张在数据管理层面依赖作者此前的工作 [1]，本文的贡献集中在执行模型与调度框架的集成；读者若要评估数据管理本身的效果，需要回到被引文献。

## 总体判断

这篇论文的论证结构是清晰的：先论证异构机器需要统一抽象（问题），再给出任务 + 数据管理 + 队列调度的设计（方案），然后用一组逐步增强调度提示的实验展示从贪婪到 w-rand 到 heft-tm 的性能变化（证据），最后用与 MAGMA 的对比和超线性现象收束（意义）。最有说服力的部分是 heft-tm 相对贪婪策略在中小规模问题上的稳定提升，以及图 3 对模型误差的鲁棒性分析——这两点共同支持"性能模型驱动的动态调度在异构平台上实用"这一核心结论。相对薄弱的是超线性的因果解释和跨平台可移植性的定量证据：前者是合理但未分离因素的推断，后者主要停留在实现层面的陈述。论文对自身局限（列表调度范式的限制、优先级收益有限）的交代是诚实的，但对性能模型在非规则任务上的适用性、以及除 CUDA GPU 外加速器的调度表现，没有展开讨论。
