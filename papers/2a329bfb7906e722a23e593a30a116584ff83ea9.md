# 容器化与 PaaS 云：轻量虚拟化如何重塑平台即服务

**原文题名：** Containerization and the PaaS Cloud（2015，DOI: 10.1109/mcc.2015.51）

## 一、作者要论证什么

这篇文章的核心主张可以概括为一句话：容器是一种面向 PaaS 的轻量虚拟化技术，它通过可移植、可互操作的应用打包，使 PaaS 从固定的专有平台演进为可跨云分布、可编排的软件平台；但这一演进目前仍受制于数据与网络管理以及抽象开发层的缺失 [page 1, page 8]。

作者 Claus Pahl 明确区分了两种虚拟化技术的定位：虚拟机（VM）解决的是硬件分配与管理问题，属于 IaaS 层面的硬件虚拟化；容器解决的是软件交付问题，属于 PaaS 层面的应用打包，同时通过共享与隔离机制也触及 IaaS [page 1]。这一区分是全文论证的起点——它决定了后续所有关于"容器为什么更适合 PaaS"的讨论框架。

作者也交代了自己的论证位置：他要在 Bernstein 关于容器部署与集群管理的讨论基础上更进一步，探讨如何把 PaaS 发展为分布式云软件平台，并讨论现有技术的成就与局限 [page 2]。

## 二、从 VM 的局限到容器的必要性

论证的第一环是"为什么需要容器"。作者给出的理由不是抽象的架构偏好，而是 VM 的具体技术负担：每个 VM 需要完整的 guest OS 镜像，加上应用所需的二进制和库，这带来 RAM 和磁盘空间压力，并且启动缓慢——文中引用启动时间可能从 1 分钟到超过 10 分钟 [page 2]。图 1 用左右对照的方式呈现了两种架构的差异：左侧是传统的 hypervisor 架构，每个 VM 携带自己的 guest OS；右侧是容器架构，多个容器共享宿主 OS 和容器引擎，只打包应用及其二进制/库 [page 2]。

这里的关键推理是：PaaS 云需要解决应用打包与管理问题，而解决方案必须建立在"安全但可移植、可互操作地共享底层平台和基础设施"的技术之上 [page 2]。容器恰好满足这一要求，因为它打包的是自包含、可立即部署的应用部件（必要时包括中间件和业务逻辑），而不是整个操作系统 [page 2]。

作者随即引入了一个对后续论证至关重要的概念：容器覆盖的是应用的一个层级或层级中的一个节点，因此多层级应用就产生了容器间依赖管理的问题。编排计划（orchestration plan）描述组件、依赖关系和生命周期，PaaS 通过代理（可能是容器运行时引擎）执行这些工作流 [page 2]。这个"容器粒度导致编排需求"的推理链条，是全文从"打包"过渡到"分布式管理"的关键桥梁。

## 三、容器如何实现轻量虚拟化：Linux 机制与镜像分层

论证的第二环是技术基础。作者以 Linux 容器（LXC）为例，说明容器依赖内核的两种机制：namespace 隔离和 control groups（cgroups）。Namespace 让进程组彼此不可见，用于进程隔离、网络接口、进程间通信访问、挂载点以及内核和版本标识符的隔离；cgroups 通过限制执行、记账和隔离来管理和限制进程组的资源访问，例如限制某个容器的可用内存 [page 2-3]。作者指出，这使容器成为宿主机上"良好的多租户公民"，并在大量隔离应用之间提供更好的隔离 [page 3]。

Docker 建立在 LXC 技术之上。作者用图 2 说明 Docker 镜像的分层结构：传统 Linux 启动时内核先以只读方式挂载根文件系统，检查完整性后切换为读写；Docker 同样以只读方式挂载 rootfs，但不切换为读写，而是用 union mount 在只读文件系统之上叠加一个可写文件系统。可以有多层只读文件系统堆叠，只有顶层可写——这就是容器本身，可以有状态并可执行 [page 3]。图 2 展示的典型分层从下到上包括：rootfs 内核镜像、Linux 发行版镜像（如 Ubuntu）、平台组件镜像（Apache、Emacs）、可写容器镜像 [page 3]。

这一技术描述支撑了一个对 PaaS 有直接意义的结论：完整 Docker 镜像构成可移植的应用容器，同时也是应用栈的构建块；由于单个镜像可以被轻易修改和分发，这种方法才是"轻量"的 [page 3]。

## 四、容器生态与粒度选择

论证的第三环是容器的实际使用方式。作者描述了容器生态系统：应用容器引擎运行镜像，仓库或注册表通过 push/pull 操作在宿主机引擎之间传输镜像；仓库在提供数以万计可复用私有和公共镜像方面扮演核心角色 [page 3]。容器 API 允许创建、定义、组合和分发容器 [page 3]。

图 3 展示了不同的容器化应用架构场景：应用运行在负载均衡器和自动扩缩器等管理组件之上（a），运行在二进制/库之上（b、c），以及运行在数据库之上（d）[page 4]。这里作者讨论了一个有实际权衡的设计选择：容器粒度（一个容器内应用的数量）。一种做法是"每应用一容器"，便于组合新栈、复用通用组件、重建和管理应用，代价是容器数量更多、交互和管理开销更大；另一种是多应用容器。作者倾向于认为容器效率应当能够承受前者的开销，但这是一个带有保留的判断 [page 4]。

数据与网络管理是容器作为分布式应用包必须解决的两个问题。Docker 通过数据卷（data volume）和数据卷容器管理数据：数据卷是容器内特殊指定的目录，绕过 union 文件系统以提供持久或共享数据，可在容器间共享和复用（图 4）[page 4]。网络管理基于两种端口分配方法：网络端口映射和容器链接（container linking）。链接允许容器间传递信息，但 Docker 依赖容器名称建立链接，名称必须唯一，这意味着链接通常限于同一宿主机（同一守护进程管理）上的容器 [page 4]。这个限制是后文讨论分布式挑战的伏笔。

表 1 从标准化、宿主/客体架构、启动过程三个维度比较了 VM 和容器 [page 4]。作者也提到安全方面的顾虑：有资料建议每个宿主机只运行一个 Docker 实例以避免隔离限制 [page 4]。作者还列举了不同操作系统和 PaaS 平台上的其他容器技术，包括 Linux 上的 Docker、LXC、OpenVZ，Windows 上的 Sandboxie，以及 Cloud Foundry 的 Warden/Garden 和 OpenShift 的 LXC [page 4]。

## 五、PaaS 的演进与容器编排

论证的第四环把容器放回 PaaS 的历史脉络中。作者提出三代 PaaS 的演进：第一代是 Azure、Heroku 等固定的专有平台；第二代是 Cloud Foundry、OpenShift 等开源方案，已围绕容器构建；第三代是 Dawn、Deis、Flynn、Octohost、Tsuru 等从零基于 Docker 构建、可部署在自有服务器或公共 IaaS 云上的平台 [page 5]。作者指出，Cloud Foundry 通过容器支持无状态应用，有状态服务运行在 VM 中；OpenShift 则不做此区分 [page 5]。

微服务架构是推动容器编排需求的重要力量。作者描述微服务将单体应用拆分为 SOA 风格的可独立部署服务，每个服务运行在自己的进程中，通过轻量机制通信，必须能够频繁、独立、按任意时间表部署，而非固定时间的同步部署。容器化为其部署和编排提供了理想机制，尤其是在 PaaS 供给的场景下 [page 5-6]。

容器集群架构是论证从单主机走向多集群、多云的关键一步。图 4 展示了基于容器和集群概念的抽象架构场景：集群由若干宿主节点组成，每个节点持有若干容器；容器可持有持续提供的服务；应用服务是来自同一镜像的容器的逻辑分组，允许跨节点扩展应用；卷用于需要数据持久化的应用；链接允许两个或多个容器（通常在同一主机上）连接通信 [page 6]。作者指出，这种配置创建了超越 Docker 等容器方案的集群服务管理抽象层 [page 6]。

集群管理架构的组件包括：通过容器支持分布式应用部署的虚拟可扩展服务节点（集群）、操作集群的 API、平台服务管理器、管理容器生命周期的代理、以及接收外部命令并转发给容器宿主的主节点服务 [page 6]。作者引用 Kratzke 对集群架构的要求，提出轻量虚拟化集群架构应提供：托管容器化服务并提供安全通信、自动扩缩和负载均衡支持、分布式可扩展的服务发现和编排、以及服务部署在集群间的迁移 [page 6]。

作者以 Mesos 和 Kubernetes 作为实例。Mesos 是 Apache 项目，将分布式硬件资源绑定为单一资源池，原生支持 LXC 也支持 Docker；Kubernetes 是比 Mesos 更高层的集群管理方案，可配置为在 Mesos 上大规模编排 Docker 容器，基于运行在 Docker 宿主上的进程将宿主绑定为集群，minions 是运行 pods（同一宿主上的容器集合）的容器宿主 [page 6]。OpenShift 已采用 Kubernetes，Cloud Foundry 使用 Diego 作为容器编排引擎 [page 6-7]。

## 六、分布式挑战与编排方案

论证的第五环是作者认为尚未解决的核心问题。分布式系统中的容器需要高级网络支持。传统上容器通过共享宿主机的地址暴露在网络上；在 Kubernetes 中，每组容器（pod）获得自己的唯一 IP 地址，可从集群中任何其他 pod 访问，无论是否位于同一物理机。这需要基于网络虚拟化的高级路由功能 [page 7]。

数据存储是另一个问题。在 Kubernetes 集群中管理容器可能因 pod 必须与其数据同处一地而在灵活性和效率上受限。作者提出需要的是将容器与存储卷配对，使存储卷无论容器在集群中的位置如何都跟随它到物理机 [page 7]。

编排场景方面，作者指出目前没有公认的编排问题解决方案。Docker 已开始开发自己的编排方案，Kubernetes 也提供将容器编排到节点的机制，但更全面的、能处理复杂应用栈编排的方案可能涉及基于 TOSCA（Topology and Orchestration Specification for Cloud Applications）的 Docker 编排 [page 7]。TOSCA 是一种基于拓扑的服务编排标准，被 Cloudify PaaS 等支持。图 5 展示了将通用 TOSCA 服务模板应用于容器和集群技术上下文的集群拓扑编排 [page 7]。TOSCA 能够实现：应用和基础设施云服务的可互操作描述、服务各部分之间的关系、以及这些服务的操作行为（如部署、补丁、关闭）的编排计划 [page 7]。

## 七、结论的边界与作者承认的局限

作者的观察部分给出了三个判断：容器目前已被 PaaS 云广泛采用；通过采用 Docker 或 Kubernetes 等新兴事实标准进行的标准化也在发生，尽管速度较慢；开发和运维仍处于早期阶段 [page 7]。作者还指出，云管理平台仍比其构建所依赖的容器平台处于更早阶段 [page 7]。

结论段中，作者明确承认仍需重大改进来处理数据与网络管理方面以及抽象开发和架构层 [page 8]。作者还提出了一个开放问题：这种分布能在多大程度上到达云边缘的小型和嵌入式设备，以及运行小型 Linux 发行版（如需要约 50 Mbytes 存储的基于 Debian 的 DSL）的设备能否支持容器宿主和集群管理 [page 8]。

这些局限是理解全文结论强度的关键。作者的核心主张——容器有巨大潜力通过轻量性和互操作性将 PaaS 技术实质性推进到分布式异构云——是一个带有明确条件的判断：它成立的前提是数据与网络管理问题得到解决，抽象开发层得以建立，且编排问题找到公认方案。作者没有声称这些条件已经满足；相反，他把这些列为"仍需重大改进"的领域 [page 8]。

## 八、论证的整体结构与关键推理步骤

回顾全文，作者的论证可以重构为这样一条链条：VM 的完整镜像带来空间和启动开销，PaaS 需要更轻量的应用打包方式（问题）→ 容器通过 namespace 和 cgroups 实现进程级隔离，通过镜像分层实现轻量打包（技术基础）→ 容器覆盖应用层级或节点，多层级应用产生依赖管理需求，需要编排计划（从打包到编排的过渡）→ 微服务架构和跨云部署进一步强化了编排和集群管理的需求（需求放大）→ 容器集群架构和 Mesos/Kubernetes 等方案提供了部分解决方案，但数据、网络和抽象开发层仍是瓶颈（现状与局限）。

这条链条中最关键的一步，是作者从"容器是轻量打包工具"到"容器需要编排和集群管理"的推理。这一步的桥接是：容器覆盖的是应用的一个层级或节点，而非整个应用，因此多层级应用天然产生容器间依赖，而依赖管理需要编排计划，编排计划需要跨主机的集群管理 [page 2, page 6]。这个推理是作者明说的，不是分析者的重建。

另一个值得注意的推理是作者对"容器替代 VM"这一说法的处理。作者在开头说容器可以在硬件资源分配通过容器完成的情况下替代 VM [page 1]，但在结论中又说 VM 最终仍是基础设施层供给 PaaS 平台和应用组件的媒介 [page 5]。这两个表述并不矛盾：容器替代的是应用打包和部署层面的 VM 使用，而非基础设施层面的硬件虚拟化。作者没有明确展开这一区分，但文本中的这两个表述共同指向这一理解。

最后需要指出，本文是一篇综述性文章，其论证力度主要来自对技术现状的梳理和分类，而非实验数据或形式化证明。文中的图表（图 1-5）是架构示意图，表 1 是特征对比表，没有定量实验或性能基准。因此，作者关于"容器有巨大潜力"的判断应被理解为基于技术特性分析的前瞻性评估，而非已被实验验证的结论。作者本人也以"仍需重大改进"的措辞保持了谨慎 [page 8]。
