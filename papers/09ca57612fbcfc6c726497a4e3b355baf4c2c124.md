# DMDX：一个具有毫秒精度的 Windows 显示程序

**原文题名：** DMDX: A Windows display program with millisecond accuracy（2003）
**DOI：** https://doi.org/10.3758/bf03195503

## 一、作者要论证什么

这篇论文的核心主张有两层。第一层是产品性主张：DMDX 是一个基于 Win32 的程序，能够以毫秒精度呈现文本、音频、图形和视频材料，并测量对这些显示的反应时（RT）[page 1]。第二层是辩护性主张，也是全文真正的论证重心：针对当时一些研究者（如 Myors, 1999）对"Windows 能否用于实时环境"的怀疑，作者要证明 Windows 的多任务特性虽然确实带来计时风险，但这些风险可以被识别、被补偿，并在实践中被压到对多数 RT 实验无关紧要的程度 [page 1]。

因此，这不是一篇纯技术说明文，而是一篇带论战性质的可行性论证：作者既描述机制，又用实测数据回应质疑。

## 二、问题的根源：多任务操作系统为什么危险

作者先诚实地把风险讲清楚，这是全文论证的起点。Windows 是多任务环境，内核会周期性地打断 DMDX 去处理网络、磁盘维护等任务；DMDX 自身也由多个线程组成（加载视频 RAM、播放声音、监视光栅位置等）[page 2]。这带来两类计时问题：

**显示同步问题。** 软件只能从视频 RAM 中相应页面被激活的时刻开始计时，而不能从信息真正出现在屏幕上的时刻计时。要做到精确，必须持续监视指示光栅状态的寄存器，但刷新完成信号非常短暂，一旦程序分心就会错过。而 Windows 内核的打断时间往往长于刷新信号本身，所以"错过刷新信号"几乎不可避免 [page 2]。

**反应计时问题。** DMDX 每毫秒轮询一次输入设备状态，但这一操作依赖 Windows 内核的多媒体计时器回调。回调间隔会因内核忙于其他任务而变化，若反应发生后的那次回调被延迟，RT 就会被高估 [page 2]。

作者没有回避这些，反而把它们作为需要被解决的对象明确列出。

## 三、关键推理：如何把不可靠变成可靠

这是全文最关键的一步，也是读者最需要看懂的地方。

**显示端的关键桥接是"高性能计时器 + 主动补偿"。** 所有 Pentium 级主板上有高性能计时器，精度达亚微秒级（1.19 MHz），且独立运行，不受当前应用影响 [page 2]。于是 DMDX 的策略是：如果错过了刷新信号，就检查高性能计时器，若距上次刷新已超过 16.666 msec（或实际刷新周期），就假定刷新已经发生并相应调整计数器 [page 2]。换句话说，它不依赖"每次都抓到刷新信号"，而是用独立时钟来重建时间线。为避免计时器时钟与光栅时钟的微小漂移，DMDX 在可能时重新与光栅同步，把漂移降到可忽略 [page 2]。

**唯一无法恢复的错误是最后一帧的刷新信号被错过**，这会使该刺激多显示一个 tick [page 2–3]。作者对此的处理是：DMDX 会排队显示缓冲（最多 24 帧），下一帧材料已预先载入视频页面，只需在当前刷新周期内任意时刻发出切换请求，切换会在刷新完成时自动发生。要发生这类错误，显示线程必须被抢占整整一个刷新周期，这在合理快速的 CPU 上"不常发生" [page 3]。作者还强调，即便发生，输出文件会记录出错的项目号和帧号以及误差大小，用户可以丢弃这些试次的数据 [page 3]。

**反应端则没有同等优雅的软件解。** 作者坦承，鼠标和键盘事件由 DirectX 通知 DMDX，因而受其变化影响；唯一真正的解决办法是安装独立硬件来检测刺激出现并精确测量到反应的时间，但这需要为每个实验站购买额外硬件，成本效益比可能很高 [page 3]。这里作者用了一个值得注意的措辞：例如"平均 61.5 msec 的误差在多数 RT 实验中大概可以安全忽略" [page 3]——这个数值在原文中作为可忽略误差的举例出现，读者应把它理解为作者对容忍度的判断，而非 DMDX 的典型误差。

## 四、证据如何支撑结论

作者的结论不是靠机制说明，而是靠一系列实测。这些测试的设计逻辑值得讲清楚。

**视频同步的可视化验证。** 构造一系列帧，每帧是一列 X，逐帧右移一列。若无同步，偶尔会出现显示不完整（如第三列只显示一半）；若同步完美，每列都应完整显示 [page 4]。这是一个用户可自行复现的定性检验。

**刷新率计时精度。** TimeDX 让显示在红、蓝背景间交替，交换由高性能计时器控制，间隔恰为刷新间隔的一半。若刷新率取值正确，红蓝分界静止；若交换偏快，分界缓慢上移；偏慢则下移。用户可据此调整并存入注册表 [page 4]。这是一个把"看不见的计时"转成"看得见的分界移动"的巧妙设计。

**显示计时精度（RSVP 测试）。** 在 166 MHz Pentium、64 MB RAM、4-MB S3 Virge 显卡、Windows 98 上，用光电晶体管置于屏幕左上角，显示 10 个词，每词两个刷新周期（该配置下 27.46 msec），视频模式 640×480、8 bpp。若一切完美，观察到的 RT 应为 10 × 27.46 = 274.6 msec 加上光电晶体管触发反应的时间。100 次测试中 DMDX 未报告任何显示错误，平均 RT 为 278.56 msec，SD 为 0.53 msec（范围 277.1–279.4 msec），误差小于 4 msec，其中大部分来自光电晶体管停表时间 [page 5]。切换到 16 bpp 后缓冲数从 12 降到 5，序列无法全部预组装，但结果几乎不变：平均 278.99 msec，SD 0.53 msec [page 5]。这一对照很重要——它说明性能不依赖于能否预先缓冲整个序列。

**反应计时精度（Test Mode 8）。** 用测试硬件每 524.3 msec 产生一次电子开关闭合（2.000 MHz 晶振除以 2 的 20 次方），近似平均词汇判断时间。在 AMD-K6 300、Riva 128 4M、64 MB RAM、Windows 98 上测试 [page 5]。表 1 给出不同输入设备在不同负载下的反应间隔频数分布 [page 5]：

- PIO12 无负载：SD = 0.84 msec
- PIO12 播放声音：SD = 0.87 msec
- PIO12 图形负载（30×250×8 bpp）：SD = 1.01 msec
- PIO12 网络负载：SD = 0.86 msec
- 鼠标无负载：SD = 0.55 msec
- 键盘无负载：SD = 5.15 msec

作者特别提醒，各条件下平均反应间隔都是 524.3 msec，但这具有误导性：一次回调延迟 1.5 msec 会使该间隔高估 1.5 msec，而下一次会低估同样多，所以真正重要的是 SD [page 5]。对 PIO12 无负载条件，这意味着 75% 的试次测量误差小于 1 msec，其余从不超过 2 msec [page 5]。Version 2 在 Celeron 400 多显示器系统上得到 SD = 0.77 msec [page 5]。

**绝对 RT 的变异性。** 用聚焦于显示器的光电晶体管触发 PIO12，反应在刺激可见后立即发生，因此观察到的潜伏期变异必然反映内核回调例程的变异。100 次试次得到 SD = 0.29 msec，意味着 95% 的观察落在 1.16 msec 区间内，"几乎正好是毫秒精度" [page 6]。

**恒定误差的处理。** 作者承认 SD 只测变异性，不测恒定误差，并指出两点：绝对 RT 很少是研究兴趣所在，通常关心的是条件间差异，此时恒定误差无关；而且很难获得独立于测量设备的"真实"RT。用光电管触发 12-V 螺线管再压下 PIO12 微开关，RT 为 18–20 msec，但由于不知道光电管、螺线管响应时间和按键行程耗时，无法真正解释这个数字，只能说恒定误差不会大于此值，且很可能小得多 [page 6]。表 2 给出各设备的最小/最大反应时间，用于按误差大小排序 [page 6]：PIO12 微开关 18–20 msec（基线），PIO12 KB 开关 31–33 msec，通用摇杆/游戏手柄 28–31 msec，MS 串口鼠标（去球）44–50 msec，MS 串口鼠标（带球）46–52 msec，旧 AT 键盘 40–47 msec，OmniKey 102 键盘 33–40 msec，廉价 Win95 键盘 33–69 msec。作者据此明确建议慎用键盘，因为不同设备间变异很大；并强调鼠标的好结果可能只适用于所测的那一只 [page 6]。

**跨操作系统的回调延迟。** TimeDX 测得 Windows 98 下回调 SD 为 0.29 msec，Windows 2000 降至 0.07 msec，Windows ME 和 XP 为 0.08 msec [page 7]。作者同时指出，Windows 2000/XP 初期的不利之处是 PIO 卡无法用作输入或输出设备，因为没有驱动，但这一情况已不再如此 [page 7]。

## 五、对质疑的正面回应

作者专门用一节回应 Myors（1999）。Myors 用键盘自动重复作为信号发生器，运行一个为 DOS 写的程序来计时按键间隔，在 Windows 95 的 DOS 窗口下 SD 为 16.0 msec，而在 MS-DOS 模式下仅 0.06 msec [page 7]。作者的反驳是：Myors 用的是为 DOS 写的程序，它本就在 DOS 下更准；正确的比较对象应是为 Windows 写的同类程序。DMDX 是专门为利用 Win32 功能而写的，而 Myors 的程序忽略了这些功能 [page 7]。这是一个方法论层面的反驳——质疑的靶子选错了。

## 六、结论在什么条件下成立

作者自己给出了明确的边界，读者应把这些当作结论的适用条件：

1. **配置依赖。** 表 1 和表 2 的数据只对所测的具体配置有效；更快的 CPU 和更高效的显卡会进一步降低变异性 [page 7]。
2. **单一应用运行。** 作者坚持精确计时时 DMDX 应作为唯一运行的应用。在加载了多个应用（杀毒、闹钟、日历、备份、邮件等）的办公桌面上，显示错误可能相当常见 [page 3]。
3. **显卡驱动质量是显示错误的主因**，而非 CPU 速度；更新驱动常能修正错误，而 500 MHz 的 CPU 几乎可保证无错显示 [page 3]。
4. **键盘结果仅供参考。** 键盘的高变异性与软件或操作系统无关，取决于具体键盘电路，不同键盘轮询速率不同 [page 6]。
5. **视频文件计时更易变。** 对 .mpg、.mov、.avi 中关键帧的 RT 测量"更受变异性影响" [page 7]。
6. **反应端无软件级完美解。** 唯一真正彻底的方案是独立硬件，但成本效益比可能很高 [page 3]。

作者最终的结论性判断是：考虑到即使简单认知操作的时间变异也很大（个体 SD 常超过 100 msec），DMDX 引入的计时噪声相对次要 [page 7]。这个论证的力度依赖于一个隐含前提——把 DMDX 的误差（亚毫秒到几毫秒量级）与认知操作的个体内变异（上百毫秒）相比。这个比较是合理的量级论证，但它成立的前提是研究关心的是条件间差异而非绝对 RT；作者在恒定误差部分已明确承认这一点 [page 6]。

## 七、需要留意的疑点

- 表 1 中键盘条件的频数分布明显偏离其他条件（508–521 区间有 89 次，526 有 152 次，527 有 321 次），与作者"键盘变异性大"的结论一致，但该分布形态异常，读者不宜据此推断键盘误差的具体分布形状。
- 作者提到"平均 61.5 msec 的误差在多数 RT 实验中大概可以安全忽略" [page 3]，这个数值与全文其他误差量级（亚毫秒到几毫秒）差距很大，且原文未说明其来源，应视为作者对可容忍误差的举例性判断，而非 DMDX 的实测误差。
- 表 2 中"PIO12 KB switch 31–33 msec"的注释称"额外 6 mm 行程"，与 PIO12 微开关基线的差异解释为行程增加，这一解释是作者给出的，未提供独立验证。

总体而言，这篇论文的论证结构是：先承认多任务系统的计时风险，再展示用独立硬件计时器加主动补偿的软件策略如何化解显示端风险，用多组实测数据量化残余误差，最后通过指出质疑者用错了比较对象来回应批评。结论的强度被作者自己限定在特定配置、单一应用运行、以及"关心条件间差异而非绝对 RT"的范围内。
